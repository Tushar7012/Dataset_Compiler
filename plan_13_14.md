## A2. Focus management on step transitions

**Why this matters and isn't optional:** `App.tsx`'s wizard is 9 steps (`project → model → goal-suggestion → goal → plan → provider → preview → progress → export`), each swapping in a whole new component with no page navigation — a screen-reader or keyboard user gets no signal that the "page" changed unless focus moves to the new step's heading. This is the single highest-value a11y fix in this part; everything in A0/A1 is presentation and testing, this is the actual missing *behavior*.

### Step A2.1 — RED: shared hook, one test

Create `frontend/src/useFocusOnMount.ts`:

```tsx
import { useEffect, useRef } from 'react'

export function useFocusOnMount<T extends HTMLElement>() {
  const ref = useRef<T>(null)
  useEffect(() => {
    ref.current?.focus()
  }, [])
  return ref
}
```

Create `frontend/src/useFocusOnMount.test.tsx`:

```tsx
import { describe, expect, it } from 'vitest'
import { render } from '@testing-library/react'
import { useFocusOnMount } from './useFocusOnMount'

function Probe() {
  const ref = useFocusOnMount<HTMLHeadingElement>()
  return <h2 ref={ref} tabIndex={-1}>Step heading</h2>
}

describe('useFocusOnMount', () => {
  it('moves focus to the ref target on mount', () => {
    const { getByText } = render(<Probe />)
    expect(getByText('Step heading')).toHaveFocus()
  })
})
```

Run it — this should already pass once written (it's a small enough hook to write correctly the first time), but the point of writing the test first is proving the hook actually does what the next step assumes. If it fails, fix the hook, not the test.

### Step B0.2 — GREEN

```python
import os
import sys
from pathlib import Path


def _default_data_dir() -> Path:
    app_name = "TuneForge"
    if sys.platform == "win32":
        return Path(os.environ["LOCALAPPDATA"]) / app_name
    if sys.platform == "darwin":
        return Path.home() / "Library" / "Application Support" / app_name
    # Linux and anything else POSIX-like: XDG Base Directory spec.
    xdg_data_home = os.environ.get("XDG_DATA_HOME")
    base = Path(xdg_data_home) if xdg_data_home else Path.home() / ".local" / "share"
    return base / app_name
```

No new dependency (`platformdirs` would do the same thing, but three `if`/`elif` branches over `sys.platform` is genuinely simpler than adding a dependency for it — this is exactly the "can it be one line [or a few]?" rung of the ladder).

## B1. `keyring` backend requirements per OS — document, don't code

`keyring>=25.0` (already the pinned dependency) auto-selects a backend per OS at runtime — nothing to fix in code. But it needs different *system-level* things present to actually work:

- **Windows:** Credential Manager, always present. No setup.
- **macOS:** Keychain, always present. No setup.
- **Linux:** needs a running Secret Service provider (`gnome-keyring` or KWallet, whatever the desktop environment already provides) — headless/server Linux with no desktop session has neither by default, and `keyring.get_keyring()` will fall back to a `fail.Keyring` that raises on every call. This is a real, user-facing setup step for Linux specifically, not a bug — document it (see B2).

No test to write here — this is an environmental fact about the `keyring` library's own backend-selection behavior on Linux, not something this repo's code controls. **Flag for whoever implements this:** if you have a real Linux box, confirm `uv run python -c "import keyring; keyring.set_password('x','y','z'); print(keyring.get_password('x','y'))"` actually works in that environment before writing the doc section that claims it does — don't just copy this plan's claim without checking it once for real.
